# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Screentime Buddy is a study project (no release planned): an Expo SDK 58 / React Native app that
tracks screen time, lets the user label hours with activities, recommends changes from those
labels, judges a weekly goal (cut screen time 3/5/10 % vs. last week) with hypothetical discount
coupons, and has an opt-in friends leaderboard. **Current focus: the browser prototype** (demo
data, simulated friends), built so the Android app can plug in real data later. Android only
for real data; every other runtime uses demo data.

Read `AGENTS.md` too. In short: Expo changes every SDK, so check the versioned docs
(`https://docs.expo.dev/versions/v58.0.0/`) instead of relying on memory, and add packages with
`npx expo install` (it picks SDK-compatible versions). `android/` is generated by
`npx expo prebuild` and gitignored: never edit it, configure native behavior via `app.json`,
config plugins, or the local module's own files.

## Commands

```powershell
npm run typecheck        # tsc --noEmit
npm run lint             # expo lint (eslint-config-expo)
npx expo-doctor          # dependency / config sanity checks
npm run web              # browser preview with demo data
```

There is no test suite. Typecheck + lint + expo-doctor are the checks to run before calling
work done.

### Machine-specific setup (Windows)

- Node is installed at `C:\Program Files\nodejs` but may not be on PATH in agent shells: prepend
  it (`$env:Path = "C:\Program Files\nodejs;$env:Path"`).
- Drive C: is nearly full, so the Android SDK, emulator (AVD `Medium_Phone_API_37.0`) and Gradle
  cache live in `D:\AndroidDev`. Dot-source `scripts/android-env.ps1` before any Android command
  (it sets `ANDROID_HOME`, `ANDROID_AVD_HOME`, `GRADLE_USER_HOME`, `JAVA_HOME` for that session
  only), then `emulator -avd Medium_Phone_API_37.0` and `npm run android`.
- The emulator needs Windows Hypervisor Platform active (check
  `(Get-CimInstance Win32_ComputerSystem).HypervisorPresent`). The user must enable it and
  restart; it's a system setting, not something to change yourself.
- The browser-pane preview config lives one level up, in `D:\Projects\.claude\launch.json`
  (`screentime-buddy-web`), because the pane reads it from the workspace root.

## Architecture

**Platform boundary: `src/lib/usage/index.ts`.** Screens only talk to the `UsageSource`
interface. If the local native module loads (`requireOptionalNativeModule` in
`modules/usage-stats/index.ts`), it's the Android implementation; otherwise (web, Expo Go, iOS)
a deterministic demo source with a realistic hourly profile is used. An iOS implementation
would go behind this same interface. iOS can't read raw usage numbers (FamilyControls only
offers threshold callbacks and sandboxed reports), which is why it isn't implemented.

**Native module: `modules/usage-stats/` (Kotlin, autolinked from `modules/`).** One core
call: `getScreenTimeBuckets(boundaries)` takes N+1 epoch-ms boundaries and returns N minute
totals. JS builds the boundaries with `Date.setHours` (`hourBoundaries`/`dayBoundaries` in
`src/lib/time.ts`), so daylight-saving days work without the native code knowing about time
zones. Hourly and daily views use the same call; Trends gets every hour of N days in one call
and sums 24-hour chunks into days. "Screen time" means screen on **and** unlocked, replayed
from `SCREEN_INTERACTIVE`/`KEYGUARD_*` events (Android 9+), with a 6h lookback to learn the
starting state. `PACKAGE_USAGE_STATS` is declared in the module's own manifest (merged into the
app at build time). It's a special-access permission granted in Settings, and `PermissionGate`
re-checks it when the app returns to the foreground. The Kotlin module has never been compiled
successfully yet: the first Gradle build failed and its log was lost.

**The app clock: `src/lib/clock.ts`.** All "now" comes from `clock.now()` / `today()` in
`time.ts`; never `new Date()` / `Date.now()` for the current time (the dev reset in
`DevClockBar` is the one deliberate exception). In dev builds every tab header has +1 day /
+1 week / Reset (`DevClockBar`); the offset is saved in the `settings` table and restored in
the root layout's `onInit`, and `onClockChange` listeners (data hook, GoalWatcher) react to
jumps. Reset deletes rows created in the simulated future (`deleteSimulatedFuture`).

**Storage: `src/lib/db.ts`.** `SQLiteProvider onInit` in the root layout runs `migrate`; schema
changes go there behind a `PRAGMA user_version` bump (v2 replaced the old daily cat/puppy
tables). Days are local `YYYY-MM-DD` strings (`dayKey`); weeks are keyed by their Monday.
Weekly goals are **versioned by `effective_from`**: switching goals inserts a row for the
current week, and judged weeks in `week_results` are never re-judged. `day_totals` caches
finished days' totals for real devices (Android keeps ~a week of events, a week-over-week
comparison needs 14 days); `days.ts` bypasses it for demo data.

**Weekly goal flow.** `GoalWatcher` (in `src/app/_layout.tsx`) runs `evaluatePendingWeeks`
(`src/lib/weekly.ts`) on launch, foreground and clock jumps. Each finished Mon–Sun week with a
goal and no result is compared with the week before; `earnedTier` (`coupons.ts`) gives the
highest tier reached if it's at least the chosen one, and a demo coupon is inserted. The newest
result pops up as `/reward/[week]`. Concurrent calls share one in-flight promise. Demo usage
has a per-week factor (0.85–1.15), otherwise weekly totals never differ enough to earn a coupon.

**Tips and friends.** `tips.ts` is pure: hourly minutes + labels → ranked tips (labelled time
is averaged over the days that label was used). `friends.ts` defines `FriendsSource`, with
simulated friends for now; a real one needs a backend. The Friends screen loads friends' data
only when `share_with_friends` is on, and ranks finished days only (on Monday: last week).

**Theming: `src/theme.tsx`.** `ThemeProvider` (inside SQLiteProvider) picks a palette from
mode (system/light/dark) × colour theme (`ACCENTS`) × tint on/off. A theme is a hue + saturation;
`buildPalette` derives background, card, border, soft highlight, chart bars and tinted text from
it with fixed lightness steps per mode (checked to keep text ≥ 4.5:1 on every surface; re-check if
you change the steps). `primary`/`onPrimary` are hand-picked per mode (pale themes need dark
button text); status colours (success/danger) never change. Tint off = neutral surfaces with
the theme only on accents. All palettes are prebuilt in `PALETTES` so each has a stable identity.
The choices live in `settings` and load in `onInit` to avoid a flash. Never import colours directly: module-level styles use
`const useStyles = makeStyles((c) => StyleSheet.create({...}))`, shared ones
`useSharedStyles()` from `components/ui.tsx`, inline colours `useTheme().colors`. Every
`<Text>` style needs an explicit colour (unset = black, invisible in dark mode). The Theme tab
and the header `ThemeToggle` edit the same state.

**Data loading: `useFocusedData(key, load)`.** Every screen loads through this hook. It reloads
on focus, on `key` change, on foreground and on clock jumps, and drops responses from older
requests (rapid day switching). Use it instead of ad-hoc effects.

Path aliases: `@/*` → `src/*`, `@modules/*` → `modules/*`. Routes live in `src/app/`
(Expo Router); non-route code stays outside it.

## Web preview notes

- `metro.config.js` adds `.wasm` assets and COEP/COOP headers. expo-sqlite runs as WebAssembly
  on web and needs both. The database lives in the browser's OPFS under `expo-sqlite/`.
- Test week rollovers with the header's dev buttons rather than overriding `window.Date`.
- Metro's watcher on this machine can miss edits made by scripts (seen after a bulk
  rewrite): if the browser runs code that doesn't match the file, restart the preview server.
- `git checkout` writes CRLF here (`core.autocrlf`): scripted multi-line find/replace must
  normalise line endings first.
- React Native Web's `Switch` is a hidden checkbox under a drawn track: when driving the
  browser, click the visible track's coordinates; clicking the checkbox element does nothing.
  Use `ThemedSwitch` (ui.tsx): on web an "on" thumb ignores `thumbColor` and needs the
  web-only `activeThumbColor`, which it passes.
- Browser-pane screenshots often lag a render behind; confirm state with page text or a
  short wait before concluding a click failed.
